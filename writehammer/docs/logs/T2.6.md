# T2.6 Cache verification and the correctness invariant

- **Goal:** a random memory-operation test against a golden memory model; then the whole T1 suite (arch-test, random lockstep, benchmarks) with caches on and off and with memory latency 1, 5, 20 and random. Accept: identical signature hashes everywhere (the correctness invariant, spec Section 4).
- **Done:**
  - Random memory-operation test against golden models: `tests/dcache_test.py` (T2.4): 51 configurations, every load and the final memory compared with a plain byte array, counters and per-line array-write counts compared with the independent Python model `tests/cache_model.py`.
  - `tests/invariant_test.py` (`make invariant`; `--quick` is in `make test`): runs the arch tests, all 13 benign workloads and random programs under nine configurations and requires identical results: caches off; caches on at memory latency 1, 5, 20; random latency (mean 10, two seeds); and three deliberately small geometries that force frequent evictions (1 KiB; 512 B with 32-byte lines; 256 B with 64-byte lines).
    - arch tests: the signature must equal Spike's in every configuration;
    - workloads (Dhrystone, CoreMark, 8 Embench kernels, memcpy_big, memset_big, storeloop): exit code, program output, a hash of the register file and a hash of **every word of main memory with the D$ overlaid on it** (so dirty lines count) must be identical across configurations;
    - random programs: registers x1..x29 and the 2 KiB data window must equal the reference model in every configuration.
  - Supporting changes: top parameters `MEM_RANDOM_LATENCY`, `MEM_SEED`; testbench parameters for geometry (`ICB`, `DCB`, `LINEB`), random latency, a run-time cycle limit (`+maxcyc`) and the memory hash.
- **Results (full run, `make invariant`, 4 m 03 s):** arch 37/37 tests identical (and equal to Spike) in all 9 configurations; workloads 13/13 identical in all 9; random 200/200 equal to the model in all 9. Control: the unmutated build passes; the four D$ mutants tried (dirty bit never set D1, dirty victims dropped D2, write-back to the wrong address D7, wrong word returned D11) each fail the test, and D1 fails all three groups.
- **Problems:**
  1. **Coverage gap found by the mutants.** D1, D2 and D7 (all break the write-back path) passed the random-program group. Root cause: the random programs' 2 KiB data window exactly equals the 2 KiB D$, so no line is ever evicted and write-back never runs in the full core. Fix: the three small-cache configurations above. D1 now fails the random group in all three of them.
  2. A first D$ debug read in the arch testbench looked at the bare word index; the images are linked at 0x80000000 and the D$ tags carry the full address, so with a write-back cache dirty lines were invisible and every caches-on arch signature was wrong (0/13). Fixed by reading at the true address (`tb/tb_arch.sv`).
  3. The random generator's data-window base was really 0xFFFFF800 (12-bit immediate overflow, CHG-015), found because the D$ tags saw the true address.
  4. The first mutant-verification runs were far too slow: a broken core hangs, and each hung simulation ran to a generous 800 M-cycle limit. The test now bounds every run (workload limit = 12x the known-good length + 2 M cycles, passed at run time; a configuration stops after the first mismatch; random programs capped at 60 000 cycles). A first attempt to run those checks also lost an hour because the laptop slept with the lid closed; jobs now write a heartbeat so a silent job is obvious.
- **Deviations:** none.
