The attack taxonomy remains the author's group's prior work (TENDRA and the Write Hammer draft). DEC-010's `crc32` finding is retained; no benign workload or attack is excluded to improve results.

`analysis/eval_matrix.py` generates a manifest from the locked benign and attack registries and the Section 7 defaults. It plans 9,723 rows: 205 NONE/no-cache/size-sweep, 41 NEVER, 41 ALWAYS, 674 D1, 3,370 D2, 674 D3 and 4,718 rate-matched PLACEBO. These are **planned**, not observed. The manifest leaves numeric calibrated thresholds blank until `analysis/calibration.csv` and `docs/T5_INTERFACE.md` arrive. Mixed workloads are included at primary `k=2`, window 10,000 cycles; benign and attack workloads get all three k values, three windows and both modes. D2 uses M=4,8,16,32,64. The 1/2/4/8 KiB size sweep uses NONE only.

**Runtime estimate before full launch:** six Phase A smoke runs took tens of seconds including compilation. At an assumed 3–10 seconds of simulation/analysis per planned row, four jobs would require roughly 2–7 hours, plus tens of minutes of unique Verilator builds and benchmark image compilation. This is an estimate, not a measured full-matrix time. The full run has not started because the final T5 detector interface and calibration are absent.

The first T6.1 commit preceded T5. This continuation commit is necessary to

The committed full launch revealed another storage issue at 96 saved rows:
Verilator retained about 134 MB of `obj/` intermediates for each roughly
280 KB cached executable. Per-workload PLACEBO rates create distinct
elaboration parameter sets, so keeping those intermediates would exhaust the
disk. The launch was stopped. After `tests/vl_tb.py` returns a completed
executable, the evaluation runner now deletes only that build's `obj/`
directory; the executable remains cached and reused. A one-time cleanup of
90 completed `tb_prog` build directories reduced `work/vltb` from 3.5 GB to
36 MB. This changes no RTL, program, threshold, or result; it does change the
runner source hash, so the saved development rows rerun when resumed. A further
T6.1 continuation commit records this fix without rewriting earlier commits.
