# T1.7 Dhrystone and CoreMark

- **Goal:** Dhrystone and CoreMark bare-metal builds that self-check their results; run in Verilator; record cycles, instructions, CPI, stall breakdown, and unofficial Dhrystone/MHz and CoreMark/MHz with iteration counts. Accept: self-checks pass; numbers in `docs/baseline.md` with exact commands.
- **Done:**
  - Verilator runner `tests/vl_runner.py` (cached builds keyed by a hash of all sources, file-locked for parallel callers). Cross-simulator check: Icarus and Verilator give identical PERF counters (cycles, retired, stalls, miss cycles) on the smoke image, caches off and on.
  - `sw/dhrystone/` (Dhrystone 2.2 from riscv-tests): the timer block read the `mcycle` CSR, which this core lacks, so `build_dhrystone.py` applies three documented patches (timer hooks to the MMIO window, the rate printout replaced by a self-check of the benchmark's own final values, util.h shim). 500 runs.
  - `sw/coremark/` (CoreMark 1.0): our port is derived from the stock `barebones` port with documented patches (clock via the MMIO window, no board init, main renamed so `wrapper.c` can give an exit code). 10 iterations.
  - `sw/rt.c`/`rt.h` (minimal printf over the MMIO PUTCHAR register), `sw/build.py` gained `LDLIBS_EXTRA` for libc.
  - `tests/bench_test.py`, `analysis/baseline.py`, `docs/baseline.md`, `make bench`.
- **Oracles:** Dhrystone: the benchmark's own "should be" values (checked in the program, exit code = mismatches). CoreMark: the same sources built natively with the host gcc and the posix port, same seeds and iteration count; seedcrc, crclist, crcmatrix, crcstate and crcfinal printed by the RTL must equal the native values (10 iterations: `0xe9f5 / 0xe714 / 0x1fd7 / 0x8e3a / 0xfcaf`).
- **Results (caches off):** Dhrystone 500 runs: 269,526 cycles, 215,022 instructions, CPI 1.253, 1.056 DMIPS/MHz (unofficial). CoreMark 10 iterations: 10,694,252 cycles, 7,463,894 instructions, CPI 1.433, 0.935 CoreMark/MHz (unofficial). `tests/bench_test.py`: 9/9: both benchmarks pass caches off and caches on at LAT 1 and 10; three known-bad cores (H1, H3, C4) each fail both benchmarks.
- **Problems:**
  1. Verilator timed out where Icarus halted. Root cause (Verilator warning `$readmem file not found`): a `parameter string` at the top feeding an untyped `INIT_FILE` parameter was not resolved as a file name, so the memories loaded nothing. Typing the module parameters as `string` fixes Verilator but breaks Icarus 12 (`Unable to bind variable IMEM_FILE in generate`). Final: every `INIT_FILE`/`IMEM_FILE` parameter untyped (works in both); both simulators then give identical results.
  2. `libgcc` for plain `-march=rv32i` is the rv64 one (no matching multilib), see T1.4; `rv32i_zicsr` is used.
  3. CoreMark's build contained two `ebreak`. Root cause: GCC 13 at -O2 proves a null dereference on one path in `core_list_mergesort`/`core_bench_list` and emits `sw zero,0(zero); ebreak`. Never executed in a correct run, but `sw/build.py` rightly rejects it. Fix: `-fno-isolate-erroneous-paths-dereference` (only stops that trap insertion). The ISA check was not loosened.
  4. `coremark_main` returns a constant (not the error count) and always logs one "Must execute for at least 10 secs" error because there is no clock. The first wrapper tried to use the return value and returned 254 for a correct run. Fix: the wrapper counts CoreMark's own "[%u]ERROR! ... crc" messages; the Python test also requires every CRC line to equal the native oracle.
  5. Dhrystone: `debug_printf` is defined (as a no-op) by the benchmark itself, so the port must not define it.
- **Deviations:** rates are unofficial (no clock, fixed iterations, simulation); CoreMark/Dhrystone sources are patched at build time from pinned third-party copies, never edited in `third_party/`.
- **Open items:** none.
