# Detecting write hammering in a modeled-NVM data cache: measurements on a 5-stage RV32I core

Every number below is generated: it comes from `analysis/results.csv` (9,723 runs) through `docs/RESULTS.md`, `docs/HYPOTHESES.md`, `flow/cost_table.md` or `docs/baseline.md`, and each row of `docs/RESULTS.md` names the run_id it was read from. Where a statement rests on something other than a generated file, the file is named.

## Abstract

We built a parameterized I$ and D$ for an existing 5-stage RV32I core and treated the D$ data array as a modeled non-volatile memory whose lifetime is set by its most-written line. We implemented three small hardware detectors, per-line counters (D1), hashed counters (D2) and a global store-rate counter (D3), together with the restricted-store action the specification prescribes (bypass the array and invalidate the line), and measured them against 24 write-hammer attack variants and 13 benign workloads, with controls (NEVER, ALWAYS and a rate-matched PLACEBO). Three results. (1) **Detection works for the counting detectors**: D1 and D2 flagged 11 of the 24 attack runs, all of them "direct" forms, with a false-positive cycle fraction of zero on every benign workload at the primary setting; D3 flagged no attack and falsely restricted a benign program. (2) **Mitigation does not**: restricting every store reduced the attack array writes by 8 % on average and by at most 20.8 %, because a bypassed store invalidates its line and the next load refills, and therefore writes, it. (3) **Cost**: D1 adds 4.0 % (1 KiB) and 5.7 % (2 KiB) to the synthesized cache area; the other variants are inside synthesis variation. The pre-registered verdicts are H1 REFUTED, H2 INCONCLUSIVE, H3 REFUTED. This is a measurement study of one core and one implementation of the attacks; it is not a claim about real SRAM caches or multicore attackers.

## 1. Motivation and scope

Non-volatile memories wear out under repeated writes, and the write-hammer family of attacks repeats writes to one location or a small set of locations until a cell fails. The author's group studies such attacks (TENDRA and the Write Hammer draft). This project asks a narrower hardware question on a single core: given only the store stream and the data-array writes of one cache, which cheap detector finds hammering, at what cost, and which one fails?

What this is not, in the specification's own words: not a claim that SRAM L1 caches are endurance-limited (it is a modeled-NVM study); not a reproduction of the multicore threat model (one core cannot tell an attacker core from a benign one); not a replication of the group's per-core drop-at-admission throttle (dropping a benign core's stores would corrupt results, so it is not implemented, and the correctness-preserving analogue, the stall-throttle action A2, was **not run**, KI-020); not a breakthrough. The attack taxonomy (RLA, RTA, RnLA, RnTA) is the group's prior work; this repository implements those definitions from the author's papers (`docs/logs/T4.2.md`) and does not claim them.

## 2. Design

**Core.** The existing 5-stage RV32I pipeline (forwarding, load-use stall, branch flush) was completed with sub-word loads and stores, MMIO performance counters and a C toolchain flow (T1, `docs/logs/T1.*.md`). It passes the riscv-arch-test subset against Spike, 1,000 random hazard-dense programs per configuration against an independent reference model, and Dhrystone, CoreMark and Embench kernels against native oracles. The CPI of the baseline (ideal memories) is in `docs/baseline.md` (for example Dhrystone 1.253, CoreMark 1.433).

**Memory system.** A line-granule main-memory model (latency 1, 5, 20 or random), a parameterized direct-mapped I$, and a write-back, write-allocate D$ (`rtl/icache.sv`, `rtl/dcache.sv`, `rtl/mem_model.sv`). The D$ emits one event per data-array write (a store hit or a line fill) and a per-request trace, which the wear monitor counts per line. Peak-to-mean ratio (PMR) over all lines and an extrapolated time to failure (`T_fail`, endurance 1e15 writes, an illustrative assumption) are computed from those counts. The correctness invariant, that the final architectural state is identical to the caches-off core, is checked for every configuration, detector, benchmark and attack that was run (`tests/invariant_test.py`, `tests/guard_integration.py`).

**Restricted-store action (A1).** A restricted store skips the data array: if the line is resident and dirty it is written back, the line is invalidated, and the store word goes straight to memory. A later load of that line misses and refills it. This is the action the specification defines, and it is the root of the mitigation result below.

**Detectors (`rtl/write_guard.sv`, DEC-011).** Each window of `W` cycles (default 10,000) the counters are cleared. D1 keeps one 16-bit saturating counter per D$ line, incremented on each data-array write; a line above `THRESHOLD` is hot and its stores are restricted until a window ends with its count below `THRESHOLD/2`. D2 does the same with `M` counters indexed by a fixed hash of the line index (XOR-fold, odd-constant multiply, bit-select; aliasing is intentional). D3 counts completed stores in one counter; above the threshold the whole store stream is restricted, latched in STATIC mode and re-evaluated each window in ADAPTIVE mode. Controls: NEVER (restricts nothing, must equal NONE in every metric), ALWAYS (restricts every store: the upper bound of what bypass can achieve) and PLACEBO (restricts a seeded pseudo-random fraction of stores equal to the real detector's measured fraction on the same workload). Thresholds are `k` times the per-window maximum on the calibration set (Dhrystone and CoreMark only) for `k` in {1.5, 2, 4}, primary `k = 2` (`analysis/calibration.csv`; the held-out set was never read for calibration).

## 3. Method

*Workloads.* Calibration: Dhrystone, CoreMark. Held-out false-positive set: eight Embench-IoT kernels chosen by a rule fixed before any detector existed (DEC-008), plus `memcpy`, `memset` and a store loop. Attacks: the four kinds, each in a "direct" and a "paper" form, randomized kinds with seeds 1 to 5, 2 M cycles each; mixed workloads of 1 M benign, 1 M attack and 1 M benign cycles. *Matrix.* 9,723 planned runs, 9,723 completed, every run with an architectural signature equal to the caches-off core (`docs/EXCLUDED_RUNS.md`). *Metrics.* False-positive cycle and store fractions are taken over the benign phases and detection latency from the start of the attack phase, both from per-phase counter snapshots (`docs/T5_INTERFACE.md`). *Integrity.* The tests are locked by hash (`scripts/check_locks.sh`, `docs/CHANGE_LOG.md`); every test was shown to fail on a mutant or a broken core (52 core mutants, 19 guard and bypass mutants, 62 checks in the guard unit test and 18 in the bypass verification); each cache model is replayed by an independently written Python model; differences smaller than the seed-to-seed range are not claimed.

## 4. Results

**4.1 Detection (RESULTS section 3).** At the primary setting D1 and D2 (every `M` from 4 to 64) detect 11 of 24 attack runs: RLA direct, the five RnLA direct seeds and the five RnTA direct seeds. They do not detect RTA direct (PMR 64.2 without a detector) or any of the "paper" forms, whose writes are spread over many lines (PMR 1.2 to 2.5 without a detector, against 20 to 128 for the detected forms). The median detection latency is about 39,000 cycles (four windows), 5,219 cycles for RLA direct and about 139,000 for RnTA direct. D3 detected no attack: its primary threshold (twice the per-window store maximum of Dhrystone and CoreMark) is 1,534 stores per 10,000 cycles, and the highest-rate attack, RLA direct, issues about 1,430 (285,718 stores in 2,000,067 cycles). D1 and D2 therefore do not show the evasion by randomization that H1 predicted; the randomized direct attacks were detected.

**4.2 False positives (RESULTS section 2).** D1 and D2 restricted no cycle on any of the 13 benign workloads at the primary setting, including `crc32`, whose whole-run PMR is 127.9 of a possible 128 (DEC-010: whole-run PMR cannot separate it from an attack, which is why the pre-registered attack-validation rule fails for 23 of 24 variants and is reported, not amended). D3 restricted `huffbench` for 98 % of its cycles in STATIC mode and 14.7 % in ADAPTIVE mode. Across the 18 registered D1 settings, 4 restrict at least one `crc32` cycle, with a maximum restricted-cycle fraction of 0.996 (`docs/HYPOTHESES.md`): a detector tuned more tightly than the calibration rule does flag it.

**4.3 Mitigation (RESULTS section 4).** With ALWAYS, every store is bypassed and no store writes the array, yet the attack array writes fall by 8 % on average (median 0.3 %, at most 20.8 %). For the direct forms the ratio is 0.9998 to 1.0: for RLA direct, 285,720 array writes without a detector become 285,716 with every store restricted, 285,713 of them refills after a bypass, so each bypassed store is followed by a refill that writes the same line. The paper forms do better but still keep 79 to 83 % of their array writes (for example RnLA paper seed 1: 142,956 to 118,165). Consequently no detector reduced any attack's PMR by 50 % (H1, H3), and H2's comparison has no eligible attack (INCONCLUSIVE by its own definition). The detectors' value as detectors is intact; the action does not deliver the wear reduction against attacks that read back.

**4.4 Controls.** NEVER matched NONE in cycles and every counter on every image (`tests/guard_integration.py`); ALWAYS bounds the effect as above; against the rate-matched PLACEBO the mean PMR reductions of the detectors (0) and of the placebo (about 1e-13 to 1e-7) are indistinguishable (RESULTS section 5); the per-run "beats placebo" flag fires in 0 to 3 of 24 runs on differences of order 1e-7, which are not claims. This is consistent with 4.3: when bypass cannot reduce writes, a random restriction and a detection-triggered one look the same.

**4.5 Sensitivity.** Windows of 1,000, 10,000 and 100,000 cycles and `k` of 1.5, 2 and 4 are in `analysis/sensitivity.csv` (1,064 measured points, 2,466 censored seeds recorded without inventing a latency) and `analysis/sensitivity.png`; no registered setting makes H1 or H3 true (`docs/HYPOTHESES.md`, registered sweep outcomes). A post-hoc windowed PMR analysis is in `analysis/exploratory_windowed.png`; it is exploratory and changes no verdict.

**4.6 Cost (RESULTS section 6).** Synthesized with Yosys 0.66 and OpenSTA 2.7.0 on sky130 in the pinned image, three identical repeats per variant. The cache pair dominates (1.10 M to 1.46 M µm² against 76,323 µm² for the core), because the arrays are flops. Synthesis variation is about 2 % of the cache: D2 with `M` of 4, 8 and 16 comes out smaller than the unguarded cache, which a design that only adds logic cannot, so deltas below about 2 % are not claims. D1 stands out: +4.0 % at 1 KiB and +5.7 % at 2 KiB of the cache, +57 % and +109 % of the core. Fmax is 5 to 10 MHz (an untuned flow with large flop-array multiplexers) and its deltas change sign between sizes, so no Fmax effect is attributed to the guard.

|---|---|---|
| H1 | REFUTED | D1 reduces no attack's PMR by 50 %; it also detects the randomized direct attacks |

| H3 | REFUTED | D3 reduces no attack's PMR by 50 %, although its false-positive condition holds (`huffbench`) |

## 6. Limitations and threats to validity

One core and one memory configuration family; a modeled NVM with an assumed endurance and clock; one implementation of each attack; a benchmark set of 13 workloads; attacks that read back their data, which is what defeats bypass-and-invalidate (an attack that never reads the line back would behave differently and was not measured); thresholds fixed by a pre-set calibration rule on two programs; action A2 not run; a core-only top and an untuned physical flow whose Fmax is not informative; synthesis variation of about 2 % of the cache area; the post-hoc analyses are labelled and do not alter pre-registered verdicts. What would change the conclusions: a restricted-store action that also stops refills of a flagged line (not implemented, would be a design change made after seeing the results, so it is future work), or attacks that never read back.
